# 启动主链路主题游

> 学习方式：问题驱动 / 断点跟栈，不逐行通读源码。  
> 范围：`NestFactory.create` → `app.listen`  
> 本日不进：`Injector` 内部细节、动态模块、Scope、微服务。

一句话先记住：**`create` 只负责「扫模块 + 造实例」；真正挂路由、开端口，是 `listen` → `init` 才做的。**

---

## 全景图（只记这一张）

```text
main.ts
  NestFactory.create(AppModule)
  │
  ├─ ① 建壳：ApplicationConfig + NestContainer + HttpAdapter
  │
  └─ ② initialize()
        ├─ DependenciesScanner.scan()          ← 只登记，不 new 业务类
        │     registerCoreModule
        │     scanForModules（递归 imports）
        │     scanModulesForDependencies
        │
        ├─ InstanceLoader.createInstancesOfDependencies()
        │     先 prototype，再真正实例化 Provider / Controller
        │
        └─ applyApplicationProviders()         ← 全局 Guard/Pipe 等
  │
  └─ ③ new NestApplication(...) 并返回代理

await app.listen(3000)
  │
  └─ 若未 init → init()
        registerModules（中间件等）
        registerRouter（路由绑到 Express）
        callInitHook（OnModuleInit）
        registerRouterHooks（404 / 异常）
        callBootstrapHook（OnApplicationBootstrap）
        httpAdapter.listen(port)               ← 端口真正打开
```

## 只需记住的 5 个函数

| # | 文件 | 函数 | 这一步在干什么 |
|---|------|------|----------------|
| 1 | `packages/core/nest-factory.ts` | `create` | 建容器，调用 `initialize`，再包装成 `NestApplication` |
| 2 | `packages/core/nest-factory.ts` | `initialize` | **核心三连**：scan → createInstances → applyApplicationProviders |
| 3 | `packages/core/scanner.ts` | `scan` | 把模块树写进容器（还没有你的 Service 实例） |
| 4 | `packages/core/injector/instance-loader.ts` | `createInstancesOfDependencies` | 真正 `new` Provider / Controller |
| 5 | `packages/core/nest-application.ts` | `init` / `listen` | 注册路由 + 生命周期钩子 + 监听端口 |

## 你怎么跟一遍（约 20 分钟）

**入口建议**：用仓库里的 `integration/hello-world`（或任意简单 integration），断点打在 `packages/core` 的 `.ts` 上，这样能进本地源码。

若用 `sample/01-cats-app`，默认依赖的是 `node_modules` 里的包，断点可能打不进本仓库的 `packages/core`。

**断点（只下这 5 个）：**

1. `nest-factory.ts` → `create` 开头
2. `nest-factory.ts` → `initialize` 里 `dependenciesScanner.scan(module)` 那一行
3. `scanner.ts` → `scan` 开头
4. `instance-loader.ts` → `createInstancesOfDependencies` 开头
5. `nest-application.ts` → `init` 开头，以及 `listen` 里 `httpAdapter.listen` 附近

跑起来后，按 F10/F11 **只跟调用栈**，不要横向翻文件。

**每停一次，看一个东西：**

| 停在 | 看什么 |
|------|--------|
| `create` | 是否已有 `container`、`httpServer` |
| `scan` 前后 | `container.getModules()` 模块数量是否增加（仍无业务实例也可） |
| `createInstancesOfDependencies` 后 | 某个 Provider 的 `wrapper.instance` 是否已有值 |
| `init` | 是否走到 `registerRouter` |
| `listen` | 端口是否在这一步才真正 bind |

## scan 和 createInstances 分别指什么

类比：**先填花名册，再给人发工牌上岗。**

以 `sample/01-cats-app` 为例：

```ts
// app.module.ts
@Module({ imports: [CoreModule, CatsModule] })
export class AppModule {}

// cats.module.ts
@Module({
  controllers: [CatsController],
  providers: [CatsService],
})
export class CatsModule {}
```

### `scan`（`DependenciesScanner.scan`）

| 项目 | 说明 |
|------|------|
| **做什么** | 读装饰器元数据，把模块树登记进 `NestContainer` |
| **主要动作** | `registerCoreModule` → 递归 `scanForModules`（跟 `imports`）→ `scanModulesForDependencies`（登记 providers / controllers） |
| **产物** | **模块图 / 花名册**：容器里知道有 `AppModule`、`CatsModule`，以及 `CatsService`、`CatsController` 这些「待创建项」 |
| **还没有** | 还没有 `new CatsService()` / `new CatsController()` 这种业务对象 |

可以想成：架子上已经贴好标签「这里将来放 CatsService」，但盒子还是空的。

### `createInstancesOfDependencies`（`InstanceLoader`）

| 项目 | 说明 |
|------|------|
| **做什么** | 按花名册真正实例化，并注入构造函数依赖 |
| **主要动作** | 先 `createPrototypes`，再 `createInstances`（对每个模块：Providers → Injectables → Controllers） |
| **产物** | **真实对象**：例如 `CatsService` 的实例已经存在，可以被注入、被调用 |
| **仍没有** | HTTP 路由还没绑到 Express，端口也还没开（那是后面的 `init` / `listen`） |

顺序必须是：**先 scan，再 createInstances**。没有花名册就不知道该造谁、谁依赖谁。

```text
create
  scan              ← 花名册（知道有什么）
  createInstances   ← 人到齐（东西造好了）
  （此时：容器里能拿到 Service 实例，但浏览器还访问不了）

listen
  └─ 自动 init      ← 挂路由、跑 OnModuleInit 等钩子
  └─ 真正 listen    ← 端口打开
```

## `wrapper` 和 `wrapper.instance` 具体指什么

### `wrapper` 是什么

Nest **不会**把你的 `CatsService` 类本身直接塞进 Map 当值。  
每个 Provider / Controller 在容器里都会包成一个 **`InstanceWrapper`**（源码：`packages/core/injector/instance-wrapper.ts`）。

调试时说的 `wrapper`，就是这个包装对象，常见字段包括：

| 字段 | 含义（直观理解） |
|------|------------------|
| `metatype` | 原来的类，例如 `CatsService` / `CatsController` |
| `name` / token | 注入用的令牌（常与类相关） |
| `scope` | 单例 / 请求级等 |
| `instance` | **真正 `new` 出来的对象**（见下） |

在模块里大致是这样存的（概念结构）：

```text
Module(CatsModule)
  providers: Map {
    CatsService => InstanceWrapper { metatype: CatsService, instance: ??? }
  }
  controllers: Map {
    CatsController => InstanceWrapper { metatype: CatsController, instance: ??? }
  }
```

`Module.providers` / `Module.controllers` 的类型就是  
`Map<InjectionToken, InstanceWrapper<...>>`。

### `wrapper.instance` 是什么

`instance` 是 `InstanceWrapper` 上的 getter/setter，指向 **该 Provider/Controller 在默认静态上下文（单例）下已经创建好的对象**。

| 时机 | `wrapper.instance` 通常是什么 |
|------|-------------------------------|
| `scan` 刚结束 | 多为 `null` / `undefined`（花名册有了，人还没来） |
| `createInstancesOfDependencies` 刚结束 | 已是真实对象，例如 `CatsService {}` |

也就是说：

- **`wrapper`** = 容器里的「档案袋」（元数据 + 生命周期状态 + 实例槽位）  
- **`wrapper.instance`** = 档案袋里放的那份 **业务实例**（`new CatsService()` 的结果）

> 进阶（本日可略过）：若是 `REQUEST` 等非单例 Scope，真正实例可能在按 `contextId` 分的槽位里；日常说的 `wrapper.instance` 默认指 **STATIC_CONTEXT（单例）** 那一格。

### 调试时怎么点到它

在 `createInstancesOfDependencies` **结束后**的调用栈里，任选一种方式：

1. 从 `modules` / `moduleRef` 进入某个模块 → `providers` Map → 点开某个 `InstanceWrapper` → 看 `instance`  
2. 或在 Debug Console 里对当前的 `moduleRef` 大致观察：`moduleRef.providers` 里某一项的 `.instance`

对比记忆：

- `scan` 后：能看到 Map 里已有 `CatsService` 对应的 wrapper，但 `instance` 仍空  
- `createInstances` 后：同一个 wrapper 的 `instance` 变成 `CatsService` 对象

## init 和 listen 的关系（对应验收第 3 题）

Nest 把「接 HTTP」和「开端口」拆开：

| 方法 | 职责 |
|------|------|
| `init()` | 中间件、**把路由绑到 Express**、`OnModuleInit`、404/异常处理、`OnApplicationBootstrap` |
| `listen(port)` | 在已准备好的 HTTP server 上真正 `listen` |

`listen` 开头逻辑大意：

> 若 `isInitialized === false`，先 `await this.init()`，再开端口。

所以你只写 `await app.listen(3000)` 时，框架会 **自动补一次 `init`**。  
也可以显式：

```ts
await app.init();      // 路由挂好，端口还没开
await app.listen(3000);
```

第二次进 `listen` 时因已初始化，不会再跑一遍 `init`。

## 本次验收（用自己的话回答即可）

1. `NestFactory.create` 返回时，HTTP 端口开了吗？
2. `scan` 和 `createInstancesOfDependencies` 谁先谁后？各自产物是什么？
3. 为什么 `app.listen()` 里还会调 `init()`？

**参考答案（大意即可）：**

1. **没开**，`create` 只做容器与实例化。
2. **先 scan，再 createInstances**。  
   - `scan` 产物 = 模块图 / 花名册（有 `InstanceWrapper`，但业务 `instance` 通常还没有）。  
   - `createInstances` 产物 = 真实对象（`wrapper.instance` 已有值，例如 `CatsService` 实例）。
3. **`listen` 负责开端口；开端口前必须先完成挂路由等，那部分在 `init` 里，所以未初始化时会先调 `init`。**
